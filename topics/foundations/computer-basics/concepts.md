## Depth vocabulary

| Depth | Means | Test |
|---|---|---|
| `aware` | You know it exists and roughly what it does | You would not be surprised by the term, and you know when to go read about it |
| `working` | You can use it correctly and explain the trade-off without notes | You can apply it to a new problem |
| `deep` | You understand the mechanism well enough to debug it and predict failures | You can explain *how* it works and where it breaks |

**Trust these markings.** Going deep on an `aware` concept is the most common way to
spend a month here and arrive no better prepared. Two concepts in this topic are
`deep`; the rest are not, and that is deliberate.

## Memory hierarchy

**Depth: deep.** The central idea of the topic.

Storage forms layers, each larger and slower than the one above:

```text
registers → CPU cache → RAM → SSD/disk → network
   small, fast  ──────────────────────►  large, slow
```

What "deep" means here, concretely — you can:

- name the layers in order
- state the approximate time to reach each one, and the ratio between adjacent layers
- explain *why* the hierarchy exists rather than just that it does (fast is small and
  expensive; there is a limited amount of "physically close")
- use it to predict which of two operations will be slower, and be right
- explain why caching appears at every level of every system as an inevitable
  consequence

**Test yourself:** why is reading a 10 MB file from disk slower than reading 10 MB
from RAM, and roughly by how much? If you cannot answer with a mechanism and a ratio,
reread [fundamentals.md](fundamentals.md#why-the-machine-is-built-in-layers) and do
the [project](../../../projects/machine-anatomy/README.md).

## Volatile versus persistent storage

**Depth: deep.** The other idea worth full attention.

RAM loses its contents when power is removed. Disks do not.

What "deep" means here — you can:

- state which components of your machine are volatile and which are not
- explain why a program loses unsaved work in a power cut, to a non-technical person
- explain why writing to disk is slower than changing a variable, as a necessary
  consequence rather than an implementation detail
- recognise that "the write returned successfully" and "the data is on the physical
  medium" are different claims, and that the gap between them is where data is lost

That last point is the seed of durability, `fsync`, write-ahead logs, and database
transactions. You do not need the mechanisms now. You do need to know that the gap is
real, because it is the reason those mechanisms exist.

## What running a program means

**Depth: working.**

The processor repeats: fetch the next instruction, decode it, execute it. Instructions
are simple — arithmetic, moving data, conditional jumps. Complex behaviour is millions
of simple instructions arranged carefully.

Take away:

- a program is *data* — instructions stored as numbers, which is why programs can be
  copied, versioned, and generated by other programs
- the machine has no judgment; it does exactly what the instructions say, which means
  every bug has a findable cause
- a "fast" computer is one that gets through this loop more times per second, which is
  why clock speed and core count are the numbers on the box

**Not needed:** pipelining, out-of-order execution, speculative execution, branch
prediction, microcode. Genuinely interesting, entirely irrelevant to you today.

## Files are sequences of bytes

**Depth: working.**

A file is bytes plus a name. It has no type. The extension is a convention that helps
programs guess how to interpret the bytes, and it can be wrong.

Take away:

- renaming `notes.txt` to `notes.png` does not create an image
- programs that check the type read the *bytes*, usually the first few, called a magic
  number
- the same bytes can be validly interpreted several ways, which is both useful and a
  security problem later
- a file's size in bytes is a real, checkable number that follows from its content

Verify it yourself — [exercises.md](exercises.md) has the drill.

## Binary and character encoding

**Depth: working.**

One bit is on or off. Eight bits are a byte, holding 256 possible values. Text is
numbers by agreement; that agreement is an encoding.

Take away:

- why 256, 1024, and 65536 recur throughout computing
- ASCII maps English characters to one byte each; Unicode covers every writing system;
  UTF-8 encodes Unicode using one byte for ASCII and up to four for others
- **the same bytes read with the wrong encoding produce garbled text** — this is the
  cause of every `Ã©` you have ever seen on a web page, and it is a bug you will fix
  more than once

**Not needed:** doing binary or hexadecimal arithmetic by hand, two's complement,
floating-point bit layout. You will meet the last one when it bites you in
`programming-fundamentals`, which is early enough.

## Rough latency numbers

**Depth: working.**

| Operation | Order of magnitude |
|---|---|
| CPU register access | under a nanosecond |
| CPU cache access | a few to tens of nanoseconds |
| RAM access | ~100 nanoseconds |
| SSD read | ~100 microseconds (1,000× RAM) |
| Spinning disk seek | ~10 milliseconds |
| Network round trip, same datacentre | ~0.5 milliseconds |
| Network round trip, intercontinental | ~150 milliseconds |

Approximate is fine and precision is misleading — these vary by hardware generation.
What must be automatic is the **ratio**: memory is nanoseconds, local storage is
microseconds, networks are milliseconds. Three thousand-fold steps.

Take away: when you hear a proposed change, you can immediately estimate whether it
moves work up or down a layer, and by how much. That estimate is worth more than most
profiling, because it tells you where to point the profiler.

## Hardware versus software

**Depth: working.**

Hardware is physical. Software is instructions — data that describes a process.

Take away: software is copyable, versionable, and changeable at effectively zero
marginal cost, and hardware is not. Nearly every economic and engineering property of
this industry follows from that asymmetry.

## What an operating system does

**Depth: aware.**

A program whose job is managing the other programs. It decides which process runs when,
hands out memory, owns access to disk and network, and stops processes interfering with
each other.

Take away: it exists, it sits between your program and the hardware, and it is the
reason one crashing program does not take the machine down.

**Do not go further here.** `operating-system-basics` (Level 0) takes the next step;
`operating-systems-fundamentals` (Level 3) does scheduling, virtual memory, and syscalls
properly. Reading about page tables today will not stick, because you have nothing yet
to attach it to.

## Processes

**Depth: aware.**

A running program with its own private memory.

Take away: hundreds exist at once, each isolated, and you can list them and stop them.
That is enough to make `top` and `ps` meaningful, which is all you need at Level 0.

**Not needed:** threads, context-switch mechanics, process states, scheduling
algorithms. All of it arrives at Level 3 with the prerequisites that make it stick.

## How CPU caches work internally

**Depth: aware.** Deliberately capped.

There is fast memory between the CPU and RAM. It holds recently and nearby-used data.
Its existence is why *how* you access data — sequentially versus scattered — affects
speed even when you access the same amount.

Take away: caches exist, and access patterns matter. That is the whole assignment.

**Explicitly not needed now:** cache lines and their size, associativity, write-back
versus write-through, coherence protocols, false sharing, prefetching. These matter
enormously at Level 3–4 in `memory-management` and `performance-engineering`, where you
will be optimising real code and can measure the difference. Today they are trivia that
will crowd out the two `deep` concepts above.

If you find this frustrating — good instinct, wrong moment. Write the question down and
come back to it when you get to `memory-management`. Keeping a list of deferred
questions is a habit worth starting today.
